# TicketsEditor architecture

## Purpose

TicketsEditor is a Windows-first, local-first, batch-oriented editor for fixing the final details of tickets generated by agents. It is not an AI rewriting service.

### Presentation contract

- The window has an integrated, flat, Borumi-like title bar with document tabs, pinned command icons, a customization plus button, draggable empty space, and native Windows caption controls. Electron uses titleBarStyle hidden plus titleBarOverlay.
- Each **tab** represents an open project/document/collection; it does not represent an individual ticket.
- Each project document has a ticket navigator, a humanized editable pane on the left, and a comfortably **pretty-printed** JSON editor on the right.
- Navigator cards display **Ticket 1**, **Ticket 2**, etc. as the main heading. Display the actual ID in muted, smaller text at the bottom-right, e.g. **ID: <dll-004>**. Filtering must not renumber cards.
- Users can multi-select tickets, search, batch edit, reorder, validate, duplicate, and export a selection or all tickets.
- Compact JSON is the **default export**. Formatted JSON and JSONL are additional output formats.
- Every ticket requires at least one specific, nonempty success_criteria entry for execution readiness. Drafts with missing fields remain editable.

## Process boundaries

1. **Electron main process** manages app lifecycle, native file operations, project registration, SQLite, hardlinks, and synchronization.
2. **Preload** exposes a minimal, typed contextBridge API. No general-purpose IPC channel is forwarded to the renderer.
3. **Svelte renderer** owns UI state, tabs, editors, navigation, selection, and commands. It cannot access Node.js, SQLite, or the filesystem directly.
4. **Shared TypeScript** contains document parsing, JSON path identification, and ticket validation, independent of Electron.
5. **SQLite** holds the complete searchable library of projects and individual tickets.
6. **Managed JSON files** provide an agent-readable project interface through .tickets.

The active SQLite database lives in Electron's userData path as tickets-editor.sqlite. The project files and managed backing files are not SQLite databases.

## Storage model

- projects: project UUID, friendly name, configured absolute root path.
- documents: project UUID, source format, complete nested JSON root. JSONL imports are represented as arrays internally, retaining source-format metadata.
- tickets: internal ticket UUID, owning project UUID, agent-defined ticket ID, sequence, RFC 6901 JSON pointer into the document, complete JSON payload.
- revisions: recorded snapshots of accepted edits for recovery.
- sync_state: canonical AppData JSON path, project .tickets hardlink path, content hash, filesystem identity, synchronization state.

Tickets can share the same agent-defined ID across different projects. A single project can temporarily have duplicate IDs while the user corrects invalid drafts; duplicates are validation issues, not silent data loss.

**Important:** the initial SQLite schema and parser are implemented. Project registration, ticket CRUD, revision creation, file watchers, FTS, and synchronization are future tasks. The schema is not proof that those workflows already exist.

## JSON documents

Import both JSON and JSONL. JSON may contain deeply nested ticket collections, other metadata, and custom keys. Index tickets by location without flattening parent structures. For JSONL, preserve the fact that it came from line-delimited JSON. The output project .tickets file is **always valid JSON**, never JSONL.

Document identity is not ticket identity. A display number is based on document order; agent ticket IDs remain unchanged after navigation or reordering. Keep unknown fields unchanged. Invalid JSON editor buffers are transient and must not overwrite last valid document state.

## Editing and sync

- One accepted document state powers the human view and the pretty JSON editor.
- Editing a field on either side produces a patch against the corresponding JSON path.
- Retain invalid text locally in the raw editor until it parses; report exact errors.
- Revision history should record accepted changes; undo/redo applies to structural edits and text edits.
- SQLite is the central indexed library. The project .tickets file is a portable interchange format.
- External edits to .tickets must be detected, parsed, validated, and merged or presented as conflicts before replacing SQLite's accepted state.
- File writes should be serialized per project. Use hashes and file identity to detect an external replacement or broken hardlink.

See ADR-0001 for the hardlink and conflict design.

## Security

Keep nodeIntegration disabled and contextIsolation enabled. Expose narrow typed IPC operations; validate input and sender identity in main. Avoid evaluating arbitrary code or interpolating untrusted ticket fields as HTML. Native file access must be limited to explicitly configured project paths.

## Planned command registry

Menu items, title-bar pinned commands, keyboard shortcuts, ticket context menus, and Alfred-like Ctrl+K / Ctrl+Shift+P command palette share a single command registry. Pinned actions should not have separate implementations.
